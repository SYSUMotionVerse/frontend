Final Verdict

这部分只陈述当前证据能支持的结论，不扩写到还没验证的端到端能力。

Evidence-backed conclusion

BlazePose-Lite 已在 mp-weixin WebGL 运行时完成模型侧可运行性验证。 稳定单帧纯推理成本约 40–50ms（p50–p95），这说明 10fps 目标在预算上具备可行性。 但当前结论仍然是 synthetic benchmark，不是 live camera E2E；本机 DevTools 环境没有可用 camera device，因此真实摄像头链路仍需真机补证。

可确认：模型加载、WebGL、warmup、推理 benchmark 已过。
未确认：真实相机帧输入、预处理抖动、设备热衰减、端到端 FPS。
适合回答的问题：“模型侧能不能跑”和“推理预算大概多少”。

What this supports

从模型侧预算看，10fps 是可讨论的目标，因为每帧 100ms 预算里，纯推理部分大约消耗 40–50ms。

What this does not support yet

它还不能证明真实摄像头链路在端到端上也能稳定维持 10fps，因为预处理、绘制、调度和热衰减都尚未计入。

Working Path

Model Loading

开发期通过 wx.request 走本地 HTTP server 读取模型；生产期需要替换为正式 OSS / CDN 托管，而不是继续依赖 localhost。

Warmup

真实 tensor warmup 可行；fake ImageData 在微信运行时里不可靠，因为缺少浏览器构造器语义。

const rgbaTensor = tf.tensor3d(frame.data, [H, W, 4]);
const rgbTensor = tf.slice(rgbaTensor, [0, 0, 0], [H, W, 3]);
rgbaTensor.dispose();
await detector.estimatePoses(rgbTensor, { flipHorizontal: false });
rgbTensor.dispose();

Dead Ends We Eliminated

这部分保留下来，是为了让后续人不要再重复走同样的路。

Dead end 01 wx.getFileSystemManager().readFile Permission denied。代码包文件不能按这里假设的方式直接读出来喂给模型。
Dead end 02 wx.request local path Invalid URL。wx.request 只接受 HTTP/HTTPS，不接受这种本地路径幻想。
Dead end 03 TF Hub built-in URLs 302 跳转到 Kaggle，拿回来的不是原始 TFJS JSON，而是 HTML 页面。
Dead end 04 Embedded base64 constants 11.8MB 体积直接撞上微信单包约束，不是一个可部署思路。
Dead end 05 Dynamic import() uni-app mp-weixin 编译器把这条路降坏了，结果不是我们想要的代码分割模块。
Dead end 06 fromPixels({ data: Uint8Array }) TFJS 在这里期待的是浏览器原生对象或不同像素打包形式，微信环境下不成立。
Dead end 07 Fake ImageData warmup 在没有真实 ImageData 构造器语义的运行时里，这条就是 plain object，最终会炸。

Next Moves

下一步不该继续在这台没有 camera device 的 DevTools 上空转，而是补真正能推进结论的环境与动作。

1

真机 camera E2E

用带可用 camera device 的真机或合适调试环境，验证真实摄像头帧输入、推理、overlay 和端到端 FPS。

2

模型生产托管

把模型文件迁移到正式 OSS / CDN，并设置缓存头；localhost 只适合开发 spike，不适合被当成部署方案。

3

帧率与预算调优

围绕 40–50ms 的模型侧预算，评估 10fps 左右的输入节流、分辨率和 overlay 更新策略。

4

如果仍然太慢

优先考虑更轻模型、更低输入分辨率、降帧率或非端侧方案。不要误把 Heavy 当成优化方向，它只会更慢。
