# 训练提醒系统设计草案

> 状态：Grill 进行中，已确认部分产品与技术决策，暂未进入实现阶段。
>
> 更新日期：2026-07-15

## 1. 背景

当前小程序已经具备前端提醒资格判断和提醒回流参数解析，但尚未真正接入微信订阅消息：

- 前端以当天有效训练次数是否少于 3 次计算 `reminderEligible`，没有按 12:00 或 18:00 判断。
- 前端可以把 `?source=reminder` 映射为提醒回流状态，但没有调用 `wx.requestSubscribeMessage`。
- 后端具备 `TrainingReminder`、`Notification` 及相关 API，但 `check_and_remind` 只创建数据库通知记录，没有调用微信订阅消息发送接口。
- 后端没有可执行的全量定时提醒任务；部署文档提到的发送函数在当前代码中不存在。
- 后端每日统计目前只计入视觉跟练，没有计入楼梯训练，不能直接作为提醒判断依据。

因此，本设计需要补齐提醒授权、统一训练计数、定时扫描、站内通知、微信推送、发送审计和提醒回流的完整链路。

## 2. 目标与范围

第一版实现以下能力：

1. 按北京时间在 12:00 和 18:00 扫描符合条件的测试参与者。
2. 同时支持站内提醒和微信订阅消息；站内提醒也是微信未配置或未授权时的兜底。
3. 统一统计武术跟练、HIIT 跟练和楼梯训练三种训练的完成状态。
4. 保证同一用户、日期和提醒时段不会被重复提醒。
5. 记录提醒资格判断、站内消息创建、微信发送结果和提醒回流。
6. 为研究管理员提供可审计的提醒发送状态。

第一版不包含：

- 学生自选每周训练日。
- 学生自行关闭站内训练提醒。
- 动作评分、心理量表或其他健康数据出现在微信提醒内容中。
- 为两个提醒时段分别申请不同的微信消息模板。
- Celery、Redis 或 Celery Beat。

## 3. 已确认的产品规则

### 3.1 每日进度

每日目标是完成三种不同训练：

1. 武术跟练；
2. HIIT 跟练；
3. 楼梯训练。

每种训练每天最多贡献 1 次有效进度。重复完成同一种训练仍保留训练记录，用于历史展示和研究分析，但不增加当日有效进度，并应标记为“重复训练，不计入今日达标次数”。

动作评分只用于训练反馈，不影响训练是否有效。一次完成提交必须带唯一训练会话 ID，以避免网络重试造成重复计数。

### 3.2 提醒时段

- 12:00：当天尚未完成任何一种训练时发送提醒。
- 18:00：当天尚未完成全部三种训练时继续发送提醒，消息中显示当前进度和未完成项目。
- 即使学生已收到 12:00 提醒，只要 18:00 时仍未完成三种训练，仍应再次提醒。
- 每名学生在每个提醒时段每天最多收到一次提醒。

### 3.3 每周停止条件

每周按周一至周日计算。在本周尚未完成 3 个达标日时，系统每天执行 12:00 和 18:00 检查；当本周已有 3 天完成全部三种训练后，本周剩余日期不再发送训练提醒。下周一重新开始计算。

第一版不增加训练日选择功能。这一规则以后可根据测试反馈扩展为自选训练日。

### 3.4 测试参与者与关闭规则

- 小程序是测试 App，不提供学生关闭站内训练提醒的开关。
- 微信订阅授权必须遵循微信平台机制，学生可以拒绝授权或在微信中关闭授权。
- 拒绝微信授权不影响学生继续使用小程序；系统继续生成站内提醒。
- 研究管理员可以将退出测试的参与者设为非活跃。非活跃参与者停止接收站内和微信提醒。

## 4. 微信订阅授权与模板

### 4.1 授权流程

注册和基线问卷完成后，在首次进入训练首页前展示提醒说明。学生主动点击“开启训练提醒”后，前端调用微信订阅授权接口。

如果学生拒绝：

- 允许继续进入训练首页；
- 保存授权状态供研究管理员查看；
- 不在每次启动时反复弹出授权窗口；
- 在训练首页提醒状态卡中提供“重新授权”入口。

### 4.2 模板策略

12:00 和 18:00 共用一个“训练提醒”模板。模板内容只包含：

- 提醒时间；
- 今日进度，例如 `1/3`；
- 尚未完成的训练项目；
- 简短训练提示；
- 点击后进入训练首页的页面路径和提醒场景参数。

模板中不包含动作评分、心理量表结果或其他健康数据。

### 4.3 上线阻塞项：长期订阅权限

当前 AppID 尚未开通长期订阅消息权限。项目上线微信提醒前，负责人必须完成：

- [ ] 在微信公众平台确认小程序服务类目满足教育类长期订阅消息要求。
- [ ] 申请并获批长期订阅消息模板。
- [ ] 记录正式模板 ID 和模板字段约束。
- [ ] 通过环境变量或服务端安全配置注入模板 ID，禁止硬编码到业务代码。
- [ ] 配置服务端获取和缓存微信 `access_token` 的能力。
- [ ] 在真实 AppID 和真机环境完成授权、发送、点击回流和拒绝授权测试。

长期订阅权限开通前采用渐进方案：

- 定时任务仍生成站内通知和提醒审计记录；
- 微信发送器在未配置模板时返回“未配置”，不能记录为发送成功；
- 开发和测试环境可以使用测试发送器验证调度、幂等与失败流程；
- 配置正式模板后启用微信发送，不改变提醒资格判断规则。

## 5. 提醒回流

学生点击微信提醒后进入训练首页。首页应展示三种训练的当日完成状态和未完成项目，不直接跳入某一种训练。

回流页面参数至少能够区分：

- 提醒日期；
- 12:00 或 18:00 时段；
- 提醒记录 ID 或不可猜测的追踪标识。

后端记录学生是否通过提醒返回小程序，用于后续评估提醒效果。回流参数不能作为训练进度或用户身份的可信数据源。

## 6. 调度与幂等

后端部署在持续运行的 Linux 服务器，时区使用 `Asia/Shanghai`。第一版使用 Django management command 执行全量提醒扫描，并由系统 cron 在每天 12:00 和 18:00 触发。

第一版不引入 Celery 和 Redis，因为当前只有两个固定执行时点。若未来增加大量动态提醒时段或异步任务，再重新评估任务队列。

每条提醒使用“用户 + 本地日期 + 提醒时段”作为业务幂等范围。数据库应通过唯一约束保证 cron 重复触发、进程重启或并发执行时不会生成重复提醒。

## 7. 发送失败与重试

- 网络超时或微信服务临时错误：最多重试 3 次，采用递增等待间隔。
- 未授权、订阅次数耗尽、模板未配置或模板参数错误：不自动重试，记录明确原因。
- 所有重试复用同一发送任务和幂等键，不生成新的提醒记录。
- 12:00 提醒不应在明显错过时段后补发；每个时段需要设置发送截止时间。
- 站内通知创建成功与微信推送成功分别记录，不能用一个布尔值混合表示。

## 8. 管理员审计需求

研究管理员至少能够按学生和日期查看：

- 12:00/18:00 是否符合提醒条件；
- 判断提醒资格时的每日进度和每周达标天数；
- 站内通知是否创建；
- 微信推送状态：待发送、成功、失败、未授权、未配置；
- 失败原因、尝试次数和最终发送时间；
- 学生是否通过提醒回到小程序；
- 学生当前是否活跃及微信授权状态。

## 9. 当前实现缺口

实施前需要重点处理以下缺口：

1. 前端 `reminderEligible` 仍采用简单的训练次数判断，没有表达三种不同训练的完成集合。
2. 前端没有订阅授权页面、重新授权入口或授权状态同步。
3. 前端 API 客户端没有接入后端通知模块。
4. 后端视觉训练会更新 `DailyTrainingStats`，楼梯训练不会更新，且现有计数模型无法表达三种不同训练。
5. 后端 `check_and_remind` 只处理当前登录用户，不是全量调度入口。
6. 后端提醒接口只创建站内 `Notification`，没有微信发送适配器。
7. 当前没有提醒幂等记录、发送尝试记录或回流记录。
8. 当前部署文档中的定时提醒示例引用了不存在的发送函数，需要在实现时修正。

## 10. 待继续 Grill 的问题

- 统一训练完成事实应建立独立模型，还是基于现有视觉/楼梯记录聚合。
- cron 扫描的参与者筛选条件及非活跃状态放在哪个模型。
- 发送截止时间和重试间隔的具体数值。
- 管理员审计能力复用 Django Admin，还是开发独立管理页面。
- 站内通知在学生端的入口、未读状态和清理策略。
- 消息记录及发送日志的保留期限。
- 提醒回流效果指标和研究导出格式。

## 11. 验收原则

最终实现至少需要覆盖以下验证：

- 单元测试：三种训练去重、每日阈值、每周停止条件、时段资格和幂等。
- 后端测试：全量扫描、并发重复执行、微信发送状态、分类重试和非活跃参与者过滤。
- 前端测试：授权接受/拒绝、重新授权、站内提醒、三种训练进度和提醒回流。
- 集成测试：训练完成写入后，12:00/18:00 扫描得到正确结果。
- 微信开发者工具及真机测试：长期订阅授权、正式模板发送、点击回流和网络失败。

在长期订阅权限和正式模板尚未开通时，只能验收站内提醒、调度、幂等、测试发送器和审计链路，不能宣称微信提醒已经完成生产对接。
